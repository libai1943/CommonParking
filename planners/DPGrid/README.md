# Dynamic programming on a nonuniform pose grid

Georg Schildbach and Francesco Borrelli, *A Dynamic Programming Approach for Nonholonomic Vehicle Maneuvering in Tight Environments*, IEEE Intelligent Vehicles Symposium, 2016, pp. 151–156, DOI [10.1109/IVS.2016.7535379](https://doi.org/10.1109/IVS.2016.7535379).

`RunPlanner('DPGrid',caseId)` returns the **Section III path planner**. This is an independent MATLAB/C++ implementation of the article's backward dynamic programming algorithm. It uses neither Hybrid A* initialization nor another planner's goal connection or smoothing. The paper's old source-download address currently redirects to Google sign-in; no author code was obtained or incorporated.

## Grid and backward search

The finite feasible configuration set includes the exact task start and goal. A coarse grid spans the bounding rectangle of all obstacle vertices and both task positions with 5 m padding. Its position spacing is 0.8 m and its 12 headings are uniformly spaced over a full revolution. A finer grid in the 6 m by 6 m square centered at the goal uses 0.2 m spacing and 24 headings; both its XY axes and heading grid are rotated by the goal heading. Duplicates and colliding poses are removed. These **uniformly applied, scene-independent resolution choices** instantiate Remark 5; the paper's experimental coarse/fine grids were specific to its map and are not universal benchmark parameters. Goal alignment was selected after an initial world-aligned development grid could not leave the target in case 9; it preserves a straight exit along any rotated goal axis and is applied identically to all cases. Grid boundaries also constrain the rear-axle sweep of each arc; this finite search restriction is not an extra physical obstacle in the frozen scene.

As recommended by Remark 6, obstacle halfplanes are shifted outward by 0.1 m. Their intersections form conservative convex miter offsets. The full common vehicle rectangle, including both overhangs, is used throughout. A blocked task endpoint is reported immediately; the original rectangular task may still be feasible without that added margin.

Search begins at the goal and adds backward-reachable layers. For every currently reached pose A and candidate position B, the circle is determined continuously by A's position/heading and B's position. Both directions around the circle are considered; straight lines are handled separately. Steering is not quantized. A candidate must obey the common curvature bound, its terminal heading must be within **0.01 rad** of B's grid heading, and its complete swept body must be collision free.

The cost is lexicographic: first the number of arcs, then their total absolute length. The entire layer is processed before stopping at a newly reachable start, so same-layer distance ties can be improved. A label already requiring fewer arcs is never replaced by a longer-arc-count route. This implements Section III-A's stated objective; the literal same-layer eligibility wording in Figure 3 could otherwise overwrite a shorter arc-count label. The C++ core groups poses sharing an XY location to avoid recomputing identical circles.

The limits are 20 backward layers and 180 s of native search. Time spent constructing/filtering the grid and formatting output is included in planner wall time but is outside the search timer. A route discovered before a time limit is returned with `budget_exhausted=true`; its distance tie-break need not be optimal because the last layer was incomplete. Exhausting the finite grid or time budget without a route is a native failure, not proof of continuous-space infeasibility.

## Swept geometry and the angular tolerance

Straight motion is checked by separating axes on its exact convex swept polygon. Circular motion uses analytic intersections of each rotating vehicle corner with obstacle edges, plus the reciprocal obstacle-vertex rotation against fixed vehicle edges. Initial overlap and tangency are rejected. Conservative exact arc bounds provide broad-phase rejection. These checks implement the article's collision-free-arc condition without choosing an undisclosed collision sample interval.

**Adjacent arcs generally have small heading jumps.** This is an explicit feature of the article, which discusses their correction in Section IV. Every returned edge retains its own reverse-search anchor and curvature. Traversing it backward preserves its actual heading, rather than snapping the arc to the neighboring node or silently concatenating it into a continuous bicycle path. Position is continuous, and each heading jump is at most 0.01 rad. The start heading may differ from the exact task heading by the same tolerance; the final pose is the exact goal anchor.

Output samples are uniformly spaced by mileage within each gear run, at most 0.05 m apart, with exact cusp positions. At a cusp coinciding with an angular discontinuity the sample retains the incoming side; both sides can be reconstructed from the native edges. Each sample includes body heading and front steering, and each interval includes forward/reverse gear. Non-cusp arc boundaries need not coincide with uniform output samples. There is **no continuous piecewise-circular geometry descriptor** because that descriptor would incorrectly erase the tolerated heading jumps. The evaluator uses its documented interpolation of this generic path.

The article also develops a particular linear/PID tracking controller and initially assumes a stop at each new arc, with a same-gear relaxation. That controller is outside this path-planner reproduction. All submitted paths receive the same benchmark rest-to-rest timing at gear changes and the same nonlinear execution evaluator. Its measured errors or collisions are distinct from the planner's collision checks. No curvature-rate continuity or executed terminal-accuracy guarantee is claimed.

## Build and validation

With a configured MATLAB C++ compiler, run `SetupCommonParking; BuildDPGrid` once. The module is cached under `tempdir/CommonParking/dpgrid/<arch>` (override with `COMMONPARKING_DPGRID_DIR`), never inside the repository. On Windows an existing Zig 0.13 executable can be supplied to `BuildDPGrid('absolute/path/to/zig.exe')`; this was the release build route. Compiler installation is not automated. The public repository contains source only, not the compiled module. The planner requires base MATLAB and the built module; the separate common evaluator uses AMPL/Ipopt.

`TestDPGrid` checks forward/reverse straight optima, a known circle, accepted/rejected heading offsets, a blocked short arc requiring its longer alternative, curvature rejection, a two-arc route, exact cusps and equal mileage, and independent dense collision checks. Release validation also checks every native arc by ODE integration, angular joins, full-body sweeps with the stated inflated obstacles, endpoints, output sampling and bounds. Results and native failures are retained for all 12 cases.
